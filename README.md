# dsh-token-dashboard

在 DSH 设置页里加一个 **Token 用量** 分区，看本机所有会话的模型调用统计。

这个插件把 DS Bot 里的用量看板单独提取了出来。它不依赖 DS Bot，也不依赖任何第三方插件。

## 功能

```
┌──────────────────────────────────────────────────────────────┐
│  Token 用量          [今天][7天][30天][90天][全部][自定义]     │
├──────────────────────────────────────────────────────────────┤
│  近 7 天          │ 缓存命中率 │   输出    │   调用次数        │
│  12.3M tokens     │   98.2%    │  22.5M    │   50,142          │
│  ↑ 12%            │            │           │                   │
│  估算成本 $120.84 │            │           │                   │
├──────────────────────────────────────────────────────────────┤
│  趋势  7 天                              [按天][按模型]        │
│  ┌ 12M ──────────────────────────────────────────┐            │
│  │    ▁▃▅▂▇▄▆                                    │            │
│  └ 0 ────────────────────────────────────────────┘            │
├────────────────────────────┬─────────────────────────────────┤
│  按模型 (5)                │  按项目 (12)                     │
│   ◕  DV  DeepSeek V4.1     │   ▬▬▬▬▬▬  Hareness              │
│   ▬▬▬▬▬▬▬▬▬  12.3M  52%    │   ▬▬▬▬    4.4B    38%           │
│   ▬▬▬▬▬▬     8.1M   34%    │   ▬▬▬     3.1B    27%           │
├────────────────────────────┴─────────────────────────────────┤
│  活跃度  182 天                       少 ▫▫▫▫▫ 多            │
│  ▪▪▪▪▪▪▪▪▪▪▪▪▪▪▪▪▪▪▪▪▪▪▪▪▪▪ (日历热力图)                     │
└──────────────────────────────────────────────────────────────┘
```

- **总览卡片**：四个格子。主格是大号 token 合计 + 涨跌徽标 + **估算成本**（品牌色加粗，
  比原来显眼得多）；另外三格是缓存命中率、输出、调用次数
- **趋势图**：按天的堆叠柱状图，两条虚线网格、悬停提示（贴近边缘时自动翻边）、
  柱子逐个入场动画，可切换「按天／按模型」
- **占比环**：用量最高模型的环形占比图，中间是该模型的头像
- **排名行**：头像 + 名称 + 单价 + 占比条 + 数值，悬停有底色。按**路由**排名，
  所以同一个模型由两个 provider 提供时会分成两行，行内显示 provider 名 —— 两者的
  单价和套餐都不同，合并会把两条不同的账算成一条
- **活跃度热力图**：GitHub 风格的日历热力图，半年视图，按天深浅表示消耗，今天有描边
- **时间范围**：今天／7 天／30 天／90 天／全部／自定义起止日期

界面照搬 DS Bot 的 Usage 页面（尺寸、圆角、间距、动画曲线都对齐），颜色全部改用
DSH 主题 token（`--dsw-alias-*`），所以明暗主题都会跟随。

## 数据来源

统计来自 DSH 的**持久会话日志**（`$DSH_HOME/sessions/`）。插件直接读取日志文件，
再按「一次计费调用」折叠成一行。

**为什么直接读文件而不是走 `sessionController`**：DSH 的会话控制器需要一个活跃的
Agent 或热的投影缓存才肯服务一个会话。历史会话两者都没有，走控制器会漏掉它们
（实测漏掉 2/3）。日志文件本身是完整的，所以插件以文件为主、控制器为备。

会话日志有**格式代次**：`session.v3.jsonl.zstd`、`session.v4.jsonl.zstd`。DSH 升级时
只把被打开过的会话迁移到新代次，没再打开过的会话仍留在旧文件里，所以插件按
`v4 → v3 → …` 的顺序探测，读到会话最新的那一代。只认 `v4` 会漏掉 153 个会话。

日志是**多帧 zstd**（每次写入追加一帧），所以用 `zlib.zstdDecompressSync` 会只解出
第一帧（实测 90 KB 的文件只解出 273 字节）。插件逐帧定位魔数 `28 B5 2F FD` 并逐帧解码。
一帧只有在其文本落在换行边界上时才被消费；正在写入的会话会留下半个帧，这部分留到
下一次扫描重读，因此不会解析出半行，也不会重复计数。

折叠规则与 DSH 自带的 `@deepseek-ai/dsh-token-meter` 的 `tokenUsage` 投影一致：

- 同一次尝试的后续采样会**替换**先前的采样，而不是相加
- `llm/retry-started` 开始一次新的计费尝试
- 模型取自最新的 `request/header` 或 `request/context`
- 被 fork 的会话，其继承自父会话的部分不计入自己

除模型调用外，`compaction/summary` 也是一次真实计费请求（一次上下文压缩要单独发一次
摘要请求）。插件把它单独记成 `kind: 'compact'` 的一行，模型取自事件自己的
`provider`/`model`，所以压缩用的模型和会话主模型可以不同。总览卡片的「调用次数」
一格会显示压缩占多少。

因为数据源是日志本身，**这个看板能看到在本插件存在之前就已经发生的调用**。

## 速度

页面**从不等待扫描**。打开时立刻返回缓存里已有的数据；扫描在后台跑，前端每 1.2 秒
轮询一次进度，扫描结束后放慢到 20 秒。

在本机 705 个会话 / 494 MB 日志上的实测：

| 场景 | 耗时 |
|---|---|
| 冷启动（空缓存，后台读完） | **约 13–15 秒** |
| 热扫描（无变动，全部跳过） | **约 0.1–0.3 秒** |
| 页面响应（缓存命中） | **约 3 ms** |
| 页面响应（缓存重建） | **约 50 ms** |
| 扫描期间最长单次卡顿 | **约 30 ms**（原来 191 ms） |

冷启动的耗时几乎全在「解压 + 解析 494 MB 日志」上，这部分只发生一次。
之后每次扫描都按字节偏移做增量：

1. 按会话日志自己的修改时间判断是否要读
2. 要读的会话，只从上次读到的字节偏移开始读
3. 只解析折叠需要的 7 类事件，其余行（工具结果、消息正文）不解 `JSON.parse`

第 3 条是关键：一整份日志解码后有 1.9 GB 文本，其中只有约 17% 的行是折叠需要的。
逐行判断类型能让解析成本降到原来的六分之一，内存峰值也不再随日志总量增长。

### 不卡住宿主

扫描在后台跑，但后台不等于不占主线程。这里有三处会让宿主掉帧，都已处理：

1. **解压**：一帧最多解出 10.8 MB，`zstdDecompressSync` 会一次占满主线程。改成流式解码，每解出 2 MB 就 `pause()`，从 `setImmediate` 里 `resume()`。解码本身在 libuv 线程池里跑
2. **拆行**：一帧拆成 JSON 行要 43 ms。改成每 1 MB 让出一次
3. **聚合查询**：一次分组查询要 65 ms，而且会挡住扫描的写入。改成按 `rowid` 分 10 段查，每段不超过 6 ms，段之间让出

实测：扫描期间最长单次卡顿从 **191 ms 降到 33 ms**，超过 40 ms 的卡顿从 82 次降到 **0 次**。

另外账本改了 WAL 日志模式：冷扫描每个会话提交一次事务，默认的 rollback journal 每次提交都要 fsync，
705 次提交要 365 ms，WAL 只要 78 ms。

### 页面轮询不重复计算

页面每 1.2 秒轮询一次。每次请求都要把 7 万条调用聚合成约 470 行，一次 65 ms。
所以聚合结果按「账本版本 + 时区」缓存，账本没变就直接返回。扫描进行中不重建
（那时账本每隔几秒就变，重建会一直重算），扫描结束后重建一次。
页面响应因此从 **84 ms 降到 3 ms**。

## 缓存

聚合结果缓存在 `$DSH_HOME/token-dashboard/usage.sqlite`。

- 表结构按「一次调用一行」存储，主键是 `session#turn:step:attempt`（模型调用）或
  `session#c<seq>`（压缩请求），所以重复扫描是幂等的
- `marks` 表记录每个会话读到哪个 `seq`、哪个字节偏移、哪个文件代的修改时间，
  用来跳过没变动的会话，也让下一次读只读增量
- 表结构带版本号；版本不匹配时插件清空缓存并从日志重建，不会读到旧结构的错数据
- **删除这个文件是安全的**，它会从会话日志重建（代价是下次要重扫一遍）

## 安装

```json
{
  "dependencies": { "dsh-token-dashboard": "link:/path/to/dsh-token-dashboard" },
  "dsh": { "profile": { "bundles": ["@deepseek-ai/dsh-base", "@deepseek-ai/dsh-web-app", "dsh-token-dashboard"] } }
}
```

在 profile 目录建好 `node_modules` 链接后，**完全退出并重开 DSH** 才会生效。

## 配置

配置写在 profile 的 `cordis.patch.yml` 里，覆盖 `token-dashboard` 这一行。全部可选。

```yaml
- id: token-dashboard
  name: dsh-token-dashboard
  config:
    home: /path/to/dsh-home          # 默认 $DSH_HOME
    database: /path/to/usage.sqlite  # 默认 <home>/token-dashboard/usage.sqlite
    prices:                          # 每百万 token 的美元单价，按 provider/model 覆盖
      'deepseek-official/deepseek-flash': { input: 0.14, output: 0.28, cacheRead: 0.014, cacheWrite: 0.14 }
```

### 关于成本估算

DSH 的模型配置里**没有单价字段**，所以单价由插件自己维护，见 `lib/pricing.js`。
解析顺序（先匹配先生效）：

1. 配置里 `prices` 的精确 `provider/model` 条目
2. `EXACT` 表的精确条目
3. `PATTERNS` 里第一个 provider 与 model 都匹配的家族规则
4. `FALLBACK` 通用兜底价

家族规则用正则匹配 model id，所以**新模型只要属于已收录的家族就自动有价**，不用改代码。
当前本机的 51 个模型路由里，47 个由精确条目或家族规则定价，4 个只落到「家族通用」规则：
`opendesign/gpt-6-luna`、`workbuddy/gpt-6-astra`（都命中 GPT 通用价 `$1.25/$10`）、
`opencode-go/kimi-k3`、`opencode-go/minimax-m3`。这 4 个在界面上会标「近似价」，
提示这个数不是该型号的真实单价。

| 家族 | 输入 / 输出（USD / 百万 token） |
|---|---|
| DeepSeek V4.1 Flash / V4 Flash | 0.15 / 0.60 |
| DeepSeek V4 Pro | 0.66 / 1.98 |
| DeepSeek V3.2 及更早 | 0.28 / 0.42 |
| GLM Flash | 0.04 / 0.50 |
| GLM 旗舰 | 0.60 / 2.20 |
| Gemini Flash | 0.75 / 3.75 |
| Gemini Pro | 2.00 / 12.00 |
| Claude Opus 5.5 | 4.00 / 20.00 |
| Claude Sonnet 5 | 2.00 / 10.00 |
| Claude Haiku 5 | 1.00 / 5.00 |
| Kimi K2 Code | 0.95 / 4.00 |
| Qwen Flash | 0.10 / 0.40 |
| GPT-5.6 Luna | 0.20 / 1.20 |
| Grok | 2.00 / 6.00 |
| Tencent Hunyuan Hy3 | 0.14 / 0.58 |
| Space Bunny | 0.50 / 0.50 |
| 免费模型（`-free` / `:free`） | 0 / 0 |

**成本卡片给两个数**：

- **实付**：只有按 token 计费的 provider 才计入。这是「真花了多少钱」。
- **套餐折算**：订阅制账号（`buddy`、`opencode-go`、`commandcode`、`deepseek-account` 等）
  按套餐计费，不是按 token 付钱。这部分数字表示「按官网价折算，消耗了多少价值」。

两者不混成一个数。本机实测 73% 的价值来自订阅套餐，混在一起会让「实付」看起来虚高。

**时段价**：DeepSeek 官方 API 分高峰/低谷价，表里是低谷价。折扣窗口是
**16:30–00:30 UTC**，其余时段翻倍。插件按时段计价，但**只对 `deepseek-official` 和
`deepseek` 两个直连 provider** 生效——转售商和订阅套餐不遵循这个时间表。
一个按季度小时聚合的分组不会被时段边界切开，所以每个分组按自己的时间点定价。

要覆盖某个模型，在配置里写精确单价：

```yaml
- id: token-dashboard
  name: dsh-token-dashboard
  config:
    prices:
      'deepseek-official/deepseek-flash': { input: 0.30, output: 1.20, cacheRead: 0.006 }
```

界面上每个模型的副标题会显示它用的单价。免费模型显示「免费」；订阅制 provider 显示
「订阅」；只命中家族通用规则的模型显示「近似价」。

## 界面语言

界面文案来自插件自己注册的词典（`lib/client.js` 里的 `en` 和 `zh`），跟随 DSH 的
界面语言切换，不是硬编码中文。

- 发布用的名称和描述来自 `locale/en.json`、`locale/zh.json` 的 `meta` 字段，
  由 DSH 的插件管理器读取。这两份文件只放 `meta`，界面文案不放在这里
- slot 声明了 `locale: 'tokenDashboard'`。DSH 的 slot 渲染器在声明了命名空间却没
  注册词典时会抛 `SlotAssemblyError`，所以词典必须和 slot 声明一起存在
- 热力图月份标题属于数据，不属于文案，用 `Intl.DateTimeFormat` 按当前语言格式化

加一种语言：在 `lib/client.js` 里加一份词典并在 `ctx.locale.register` 中登记即可。
两边的键必须完全一致；`test/i18n.test.js` 会检查键的齐全性和调用点。

## 已知限制

- 成本是估算值，不是账单
- 只统计本机 `$DSH_HOME` 下的会话
- 项目名取工作目录的最后一段，重名目录会合并
- 会话日志被外部工具改写时，`seq` 出现断档会让该会话被跳过并记一条警告（宁可少算也不重复计算）
- 一个正在写入的会话，最多比看板落后一次扫描（默认 5 秒）
- 会话目录名是**有损编码**：连续的分隔符会被折叠成一个 `-`，所以从目录名反解
  出的路径可能和真实路径不同。插件优先用日志首行的 `cwd` 字段，只有首行不可用时
  才退回目录名
- 会话目录被删除后，它的用量会在下一次扫描时从账本里清掉；如果整个会话目录暂时
  读不到（权限、网络盘），插件不会清理，避免误删
- 归档会话没有单独区分：看板统计全部会话，包括侧边栏里已归档的
